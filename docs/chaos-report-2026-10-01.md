# Отчёт о влиянии аннотаций: зона `ru-central1-a`

**Дата прогона:** 2026-10-01
**Зона:** `ru-central1-a` (изоляция SG и chaos-тесты выполняются только для неё)
**Источник данных:** аннотации Grafana + метрики VictoriaMetrics
**Сбор:** `RUN_FROM=<epoch начала прогона> ZONES=ru-central1-a scripts/collect-chaos-report.sh`
**Сырые данные:** `.state/chaos-report-2026-10-01/` (`windows.tsv`, `analysis.tsv`, `*.tsv`)

## Методика

Скрипт `scripts/collect-chaos-report.sh` (гибридный подход) забирает из Grafana:

1. все аннотации за окно прогона и классифицирует их на `chaos` (шаги pod-kill/loss/delay/isolate) и `sg`
   (isolate/restore/verify по node group);
2. для каждой аннотации запрашивает batched-запросом в VictoriaMetrics полный набор метрик эффекта;
3. считает по каждой метрике `pre`-окно (равное по длительности окну события, непосредственно перед ним) и `event`-окно.

**Окна:** для chaos — от аннотации `start` до `start` следующего шага (сбой + покой); для SG — от `start` до `end`
самой операции. Порог «существенное изменение» не задан — значение трактуется по форме кривой, как в README.

Интерпретация (этот файл) сделана AI по `analysis.tsv`.

**Метрики эффекта:** `loadgen` ошибки и rps, `loadgen` p50/p99 bulk/search; ES cluster health/шарды/документы;
ES thread pool и pending tasks; связность goldpinger (unhealthy, p99) и Cilium (avg/max latency).

> Оговорка по данным: baseline ошибок у loadgen обычно нулевой, поэтому рост с нуля даёт `inf%` в `delta_pct`.
> Абсолютные значения (`pre_max → ev_max`) информативнее. Низкоуровневые метрики (`es_nodes`, `es_docs_load`) у
> экспортёра дискретны и при коротких SG-окнах дают артефакты (например `0`), их следует читать как «данных мало».

## Ключевые находки

1. **Основной вклад даёт изоляция зоны `a` и как chaos-шаг, и как смена SG на `app-a`** — оба события дают одинаковую
   картину: ошибки до ~20–32%, пропускная способность падает на ~82%, p99 упирается в 10s, кластер `red`, `unassigned` 24.
2. **`pod-kill` второй по силе** — через `unassigned shards` (0→108) и кратковременный `red`/`yellow`, но запись/чтение
   продолжаются, потерь документов нет.
3. **`loss` и `delay` видно по латентности, а не по ошибкам:** p99 растёт до 10s (loss) и ~2.5s (delay) при ошибках < 0.5%.
4. **Смена SG на одном узле (master/data) сама по себе слабо влияет на нагрузку** — решающей становится изоляция
   `app-a` (ноды, с которой идёт трафик loadgen).
5. **Связность (goldpinger/Cilium) — самый чувствительный индикатор изоляции:** `unhealthy` 0→15, Cilium max latency
   до 15.4s. Это подтверждает, что зона действительно отрезана.
6. **Потерь данных нет:** `es_docs_load` на всех шагах только растёт. По завершении restore кластер возвращается к `green`.

## Замечания к качеству данных

- `pod-kill` задевает поды loadgen: в окне шага счётчики успевали сброситься (видны провалы `es_nodes`/`docs`).
- Короткие SG-окна (30–60 c) при `STEP_QUERY=30` дают 1–2 точки на метрику — по низкоуровневым метрикам ES
  (`es_nodes`, `es_docs_load`, `es_index_ms`) это шум; по `loadgen`/goldpinger они валидны.
- Окно `sg app-a isolate` оборвано началом chaos-изоляции (аннотация `chaos isolate` поверх), поэтому часть
  ES-метрик в нём отсутствует.
- Для повторного прогона отчёта задавать `RUN_FROM` = epoch начала прогона; иначе окно по умолчанию — последние 24 ч.
