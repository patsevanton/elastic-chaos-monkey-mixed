# Отчёт о влиянии аннотаций: зона `ru-central1-a`

**Дата прогона:** 2026-10-03
**Зона:** `ru-central1-a` (изоляция SG и chaos-тесты выполняются только для неё)
**Источник данных:** аннотации Grafana + метрики VictoriaMetrics
**Сбор:** `RUN_FROM=<epoch> ZONES=ru-central1-a scripts/collect-chaos-report.sh`
**Сырые данные:** `.state/chaos-report-2026-10-03/` (`windows.tsv`, `analysis.tsv`, `*.tsv`)

## Методика

Скрипт `scripts/collect-chaos-report.sh` забирает из Grafana аннотации прогона, классифицирует их на
`chaos` (pod-kill/loss/delay/isolate) и `sg` (isolate/restore/verify по node group), для каждой
запрашивает в VictoriaMetrics метрики эффекта и считает `pre`-окно (равное событию, непосредственно перед ним)
и `event`-окно. Порог «существенное изменение» не задан — значение трактуется по форме кривой, как в README.

Колонка **Дашборд → панель** указывает, в каком дашборде и на какой панели видна метрика события;
ссылка на дашборд открывается за окно `pre + event`. Колонка **График** — ссылка на Grafana Explore
(datasource `VictoriaMetrics`) с теми же метриками за то же окно. Колонка **Вывод** и раздел «Ключевые находки»
дописывает AI по `analysis.tsv` и графикам.

> Оговорка: baseline ошибок у loadgen обычно нулевой, рост с нуля даёт `inf%`. Низкоуровневые метрики ES
> (`es_nodes`, `es_docs_load`) дискретны и в коротких SG-окнах дают артефакты — читать как «данных мало».

## Ключевые находки

**Запись и поиск пережили все шаги.** Максимум по зоне `a`: `bulk_err_pct` 0.47%, `search_err_pct` 3.58% (оба — на шаге `isolate`, отдельные всплески на минуту). На pod-kill/loss/delay ошибки не превышали 0.5%. Ни один шаг не остановил нагрузку.

**Сильнее всего измерение задевает `isolate`.** Полный сетевой отвал зоны `a` — единственный шаг, где виден каскад: `goldpinger_unhealthy` 0 → 20 нод, задержка пинг-сетки `cilium_max_s` до 15.3 с, `es_nodes` 27 → 12 живых, unassigned до 70, `es_health_red` avg 0.73. При этом приложение продолжало писать и читать через оставшиеся зоны — деградация по ошибкам осталась в десятых долях процента.

**`pod-kill` — самый шумный для кластера, но не для приложения.** Убийство подов каждые 30 с давало максимальный рост unassigned (avg 3.2 → 10.7, пик 105), pending-tasks и разовые `red`; ошибки при этом умеренные (max ~0.4–0.5%). Массовое перераспределение шардов — основная цена, а не отказ запросов.

**`loss` и `delay` бьют по хвосту латентности, а не по ошибкам.** Потеря 30% подняла `bulk_p99_s` avg 0.26 → 1.81 (max 10) и `search_p99_s` 0.16 → 0.78 (max 5.02) при нулевых ошибках. У `delay` pre-окно оказалось выше event-окна (остаточный хвост прошлого шага), поэтому средний p99 формально падал — сравнивать надо max, а не avg.

**Вклад SG-изоляции по нодам нарастает.** `elastic-master-a` — эффекта нет; `elastic-data-a` — первые ошибки (~0.005%) и просадка `search_ok_rps` 2.23e3 → 1.97e3; `app-a` — самый сильный удар по измерению: `bulk_ok_rps` 1.12e3 → 798 (−29%), `search_ok_rps` 2.08e3 → 1.29e3 (−38%), ошибки до 0.043%. После поочерёдного `restore` все метрики вернулись к baseline.

**Автовосстановление подтверждено.** После `restore-zone.sh` кластер снова `green`, 9 нод Ready, `es_nodes` возвращается к 27, NLB обоих кластеров принимают зону. Ручного переселения шардов не делалось. `_count` индекса `load` монотонно рос весь прогон — потерь документов не видно.
